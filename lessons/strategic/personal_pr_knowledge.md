## Case 2: pydantic/pydantic#13464

**挑战**：一个真实的 bug fix（`is_bug_fix=True`），修复 computed field names 泄漏到 extras 的问题，+49 行，2 个文件——被关闭。

**pr-genius 硬性上下文**（CLI 拿不到）：
- `signals`: `is_bug_fix=True`, `is_small_pr=True`, `has_comments=True` — 有信号但缺关键项
- `has_issue_link: false`、`has_description: false`、`has_reviews: false`
- 同仓库 12 个 anti-pattern，12 个都是 `closed_rejected`（`anti-patterns/pydantic-pydantic-*.json`）
- 同仓库 10 个 success pattern，全部有 `has_reviews=True` 或 `has_description=True`

**如果没有这种结构化上下文，会怎样**：
1. 搜索 "pydantic contribution guide" → 找到指南，但不会告诉你"没 issue link 的 PR 一律拒绝"
2. 通用建议 "fix real bugs, not typos" — 这个 PR 就是 real bug，还是被拒了
3. 不知道 pydantic 维护者的核心筛选逻辑：`has_issue_link` + `has_description` 是硬门槛

**靠 pr-genius 上下文拍出来的判断是什么**：

pydantic 的 10 个成功案例 vs 12 个失败案例，信号分布完全不同：
- 成功：`has_reviews=True` 占比 40%（4/10），`has_comments=True` 占比 40%
- 失败：`has_reviews=True` 占比 0%（0/12），`has_issue_link=False` 占比 100%

成功案例不一定有 description，但 40% 有 reviews；失败案例 100% 没有 reviews、没有 issue link。
这个 PR 的 `has_reviews=False` + `has_issue_link=False` 直接命中失败模式。

```json
// anti-patterns/pydantic-pydantic-13464.json
{
  "signals": {
    "has_issue_link": false,
    "has_description": false,
    "is_bug_fix": true,
    "is_small_pr": true,
    "has_comments": true
  },
  "metrics": { "files_changed": 2, "additions": 49, "deletions": 0 }
}
```

**教训一句话**：pydantic 的门槛不是"代码质量"，是"结构化上下文"——没 issue link、没 description 的真实 bug fix，跟零信号 PR 一样被拒。

## Case 4: fastapi/fastapi#16036

**挑战**：一个 1 行 docs fix（"To do it we use" → "To do this we use"），category = `closed_already_done`——不是被拒绝，是已经有人做过了。

**pr-genius 硬性上下文**（CLI 拿不到）：
- `signals`: `is_docs_only=True`, `is_bug_fix=True`, `is_small_pr=True`, `has_comments=True`
- `category: closed_already_done` — 关键：不是 rejection，是 duplicate
- 同仓库 5 个 `closed_already_done`，8 个 `closed_rejected`，2 个 `closed_duplicate`
- 反模式命中：`anti-patterns/contribai-duplicate-pr.md:key` — "already exists", "implemented in main"

**如果没有这种结构化上下文，会怎样**：
1. 搜索 "fastapi docs contribution" → 找到指南，但不会告诉你"先搜 main 分支"
2. 通用建议 "fix real documentation issues" — 这个就是 real issue，还是白做
3. 不知道 fastapi 有 5 个 `closed_already_done` — 维护者自己在改 docs

**靠 pr-genius 上下文拍出来的判断是什么**：

fastapi 的 category 分布：`merged_success=11`, `closed_rejected=8`, `closed_already_done=5`, `closed_duplicate=2`。
`closed_already_done` 占比 19%——每 5 个被关闭的 PR 中有 1 个是"已经做过了"。

反模式库记录了自检清单：
```
- gh search prs --state all "<keyword>"
- gh search issues --state all "<keyword>"
- git fetch origin main && git log origin/main
```

```json
// anti-patterns/fastapi-fastapi-16036.json
{
  "signals": {
    "is_docs_only": true,
    "is_bug_fix": true,
    "is_small_pr": true,
    "has_comments": true
  },
  "metrics": { "files_changed": 1, "additions": 1, "deletions": 1 }
}
```

**教训一句话**：`closed_already_done` 不是 rejection，是 wasted effort；提 PR 前跑 `git fetch origin main && git log` 可以省掉 19% 的无效提交。

## §7 自查工具

```bash
# 安装 pr-genius
pip install -e ~/repos/pr-genius/prgenius

# 分析一个 PR 的信号
python3 -m prgenius analyze "<title>" --repo {owner/repo} --body "{body}"

# 检查是否命中 anti-pattern
python3 -m prgenius coach "<title>" --repo {owner/repo} --body "{body}"
# exit 0 = pass, exit 1 = fail

# 查看仓库 profile（如果有）
python3 -m prgenius profile get {owner/repo}

# 直接查 anti-pattern 库
grep -l "trigger_keyword" ~/repos/pr-genius/anti-patterns/*.md

# 查 success-pattern 库
python3 -c "
import json, os
for f in sorted(os.listdir('success-patterns')):
    if not f.endswith('.json'): continue
    with open(f'success-patterns/{f}') as fh:
        d = json.load(fh)
    if d.get('lessons'):
        print(f'{d[\"repo\"]}#{d[\"pr_number\"]}: {d[\"lessons\"]}')
"
```
